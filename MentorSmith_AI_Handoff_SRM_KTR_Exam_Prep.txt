============================================================ 1. PRODUCT
VISION ============================================================

MentorSmith should become a Linux-first programming tutor with a focused
exam-preparation mode for SRM KTR students, especially first-year CSE
students. It should also teach programming fundamentals to students from
allied branches who want to learn coding.

Two connected product areas:

A. EXAM PREP - Organised, syllabus-mapped question banks. - Verified
previous-year questions (PYQs), only when a legitimate source and the
exact paper/session are known. - Important practice questions selected
from syllabus coverage, concept importance, and analysed historical
papers where available. - Clearly labelled predicted PRACTICE questions
generated from the syllabus, permitted source material, and observed
question patterns. - Worked solutions and explanations. - Timed mock
tests matching a documented exam pattern when that pattern is
verified. - Topic-wise performance, mistake analysis, weak-topic
revision, and adaptive practice. - Clear distinction between verified
past questions, original practice questions, and uncertain predictions.

B. CODING ACADEMY - Beginner-friendly learning paths for programming,
initially prioritising C and Python if those match the user’s actual
target course and validated curriculum. - Real compiler/interpreter
feedback, output prediction, code tracing, debugging, progressive
exercises, and lab-exam practice. - Friendly learning path for CSE and
allied-branch students who want to learn coding. - Reuse the current
evidence-based mastery engine where it is appropriate; do not create a
disconnected duplicate learning system without a reason.

Do not reduce MentorSmith to a generic chatbot or a PDF summariser. Its
differentiation should be structured practice, correctness, transparent
source provenance, and adaptive revision.

============================================================ 5. QUESTION
BANK: REQUIRED MODEL AND WORKFLOW
============================================================

Every question must have stable identity and provenance. Suggested
fields (adapt to existing architecture rather than blindly imposing a
new schema):

-   question_id
-   course_id
-   unit/module/topic/concept IDs
-   question_text
-   question_type (MCQ, short answer, long answer, numerical, code
    tracing, debugging, programming, etc.)
-   difficulty and estimated time, where meaningful
-   marks and expected answer length only if verified or clearly marked
    as a configurable practice estimate
-   answer / reference solution
-   explanation / marking rubric
-   accepted variants or test cases, where appropriate
-   source_type: VERIFIED_PYQ | OFFICIAL_SAMPLE | ORIGINAL_PRACTICE |
    PREDICTED_PRACTICE
-   source_title / source_file / URL / page / question number
-   exam/session/date if known
-   verification_status and verified_by/verification date where
    appropriate
-   content rights / redistribution status
-   tags and prerequisite concepts
-   confidence/reasoning metadata for generated practice questions (not
    a fake probability of appearing in an exam)
-   created/updated timestamps
-   content version

Workflow: 1. Import syllabus and permitted papers/material. 2.
Parse/extract candidate questions without silently modifying the
original text. 3. Keep a source excerpt or source pointer so a human can
compare the extracted item with the source. 4. Mark uncertain
OCR/parsing for manual review. 5. Human verifies exact PYQ wording,
answer, marks, year/session and provenance before it is labelled
VERIFIED_PYQ. 6. Generated questions must be checked for syllabus
alignment, correctness, duplicate similarity, ambiguity and answer
validity. 7. Keep generated content distinct from original sourced
material. 8. Permit editing, correction, deactivation and versioning of
erroneous questions. 9. Provide a report/export of unverified,
missing-source, duplicate or possibly incorrect questions. 10. Never
fabricate a year, exam session, marks allocation, official answer key,
or source.

Question quality: - Answers should show reasoning, not only final
results. - For code questions, execute tests where feasible; include
edge cases and explain expected output. - For MCQs, verify there is one
defensible correct answer unless the question explicitly permits
multiple answers. - For long answers, provide a transparent rubric and
explain that AI grading is approximate. - Where a question depends on a
diagram, table, or equation, preserve it accurately and check
rendering. - Use deterministic grading for objective/programming answers
where feasible; use rubric-assisted grading for free-text answers with
uncertainty disclosed. - Include difficulty and concept tags without
claiming objective precision unless calibrated.

============================================================ 6.
PREDICTED QUESTIONS: SAFE, HONEST DESIGN
============================================================

Do not promise that any generated question will appear on a real exam.

Predicted practice questions should be generated from: - Verified
official syllabus and learning outcomes. - Topics/concepts represented
in available permitted past papers. - Coverage gaps in the student’s
preparation. - Documented exam format, if verified. - Important
prerequisite concepts and common misconceptions. - Question patterns
that can actually be supported by the available paper set.

Every prediction should display: - “Predicted practice — not an actual
past question.” - Why it was generated (e.g., syllabus topic, concept
not yet practised, or pattern observed in N verified papers). - Which
syllabus unit/concept it covers. - Whether any pattern analysis is based
on a small sample. - A warning that real exam questions may differ and
the student should study the full syllabus.

Do not display fake precision such as “97% chance of appearing” unless a
defensible, calibrated statistical method and sufficient data support
it. Prefer transparent qualitative labels such as “high syllabus
priority” or “useful practice” with an explanation. “High priority” must
not imply certainty of exam appearance.

Pattern analysis: - Only calculate topic frequencies from papers with
verified provenance. - Show sample size and coverage years/sessions. -
Distinguish “appeared in this dataset” from “likely to appear again.” -
Avoid leakage or training/evaluating on the same papers when validating
prediction claims. - Do not imply past frequency guarantees future
appearance.

============================================================

Stage 0 — Audit and report. Do not skip this. Establish the real
codebase state and identify the highest-priority blockers.

Stage 5 — Predicted practice. Only after verified syllabus mapping and a
trustworthy question bank exist. Explain why each question was
generated; label it honestly; check answer correctness and duplicates.

Stage 6 — Pilot. Test with a small volunteer group. Ask about usefulness
and willingness to pay. Collect only necessary, consented, anonymised
feedback. Do not claim success without results.

Stage 7 — Distribution and monetisation. Choose desktop/web/mobile
distribution based on user research. Before charging, establish content
rights, privacy policy, terms, AI cost controls, payment security,
refund/support process, and reliable product behaviour.

Do not start Stage 7 while core correctness and provenance are
unresolved.
